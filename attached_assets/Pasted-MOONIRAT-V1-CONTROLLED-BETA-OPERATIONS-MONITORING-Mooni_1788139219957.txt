* Authentication
* RLS
* Storage policies
* admin authorization
* feedback ownership
* creator ownership
* video ownership
* playlist ownership
* watch-history isolation
* moderation authorization
* verification authorization
* service-role isolation
* upload recovery

* qualified view tracking
* pagination
* invalid media handling
* mobile navigation
* logout/login behavior

Use real Supabase data only.

PHASE 3 — CONTROLLED BETA CONFIGURATION

Design the beta for a LIMITED group.

Recommended initial cohort:

* 10–25 creators
* 50–100 viewers/followers
* invitation-only access
* controlled onboarding
* active feedback collection

Do NOT open unrestricted public registration yet.

If the existing application does not support invitation-only access, DO NOT invent a large new system just for this. Document the limitation and recommend the safest existing approach.

PHASE 4 — BETA OBSERVABILITY

Verify that the existing system can accurately measure:

* signups
* active users
* creator profiles created
* videos uploaded
* videos published
* video starts
* qualified views
* watch completion where already supported
* follows
* playlist creation
* feedback submissions
* verification applications
* moderation actions
* upload failures
* playback failures

Do not add unnecessary analytics infrastructure.

Use existing Supabase tables/events where possible.

PHASE 7 — ISSUE TRIAGE

Create a strict classification:

P0 = security, data loss, app unusable
P1 = core viewer/creator journey broken
P2 = important usability/reliability problem
P3 = cosmetic or minor improvement

Only P0/P1 issues authorize immediate engineering changes during the beta.

P2/P3 issues should be collected and reviewed after sufficient beta evidence.

FINAL RULE:

Moonirat V1 is now a product-validation phase.

The goal is NOT to keep building.

The goal is to prove:

1. Viewers return.
2. Viewers watch.
3. Viewers follow creators.
4. Creators upload.
5. Creators return and upload again.
6. The platform remains reliable under real usage.
7. Users report problems and the team can resolve them.

Only build when real beta evidence shows something needs to be fixed.

STOP after completing the beta operations audit and documentation.
