P0 — DURABLE VIEW TRACKING

Audit the existing video view implementation.

The view threshold and cooldown must be enforced server-side/database-side.

Requirements:

* View only becomes valid after the existing watch threshold.
* Existing 24-hour cooldown must remain.
* Refreshing the page must not create duplicate views.
* Repeated playback attempts must not bypass the cooldown.
* Client-side state/localStorage must NOT be the security mechanism.
* Playback errors must never create a valid view.
* Seeking must not trivially manufacture a view.
* Anonymous/signed-out viewing behavior must follow the existing V1 rules.
* Preserve current analytics behavior.

Use Supabase RPC/database logic where appropriate.

Do not expose service-role credentials to the browser.

Test with real Supabase data.

⸻

P0 — LEAKED PASSWORD PROTECTION

Verify the current Supabase Auth security configuration.

Enable Supabase leaked-password protection if it is available through the project’s supported configuration.

If this cannot be enabled through the available MCP/API tooling:

* DO NOT fake completion.
* Document exactly what must be enabled manually in Supabase.
* Keep the application code unchanged unless necessary.

The final report must clearly state:

LEAKED_PASSWORD_PROTECTION = PASS / MANUAL_ACTION_REQUIRED

⸻

P0 — ADMIN STORAGE CLEANUP

When an authorized admin removes a video:

1. Verify admin authorization server-side/database-side.
2. Remove the database record safely.
3. Remove the associated video Storage object.
4. Remove the associated thumbnail Storage object when applicable.
5. Handle missing Storage objects gracefully.
6. Do not allow ordinary users to delete arbitrary Storage objects.
7. Prevent orphaned files whenever possible.
8. Preserve auditability of the moderation action.

IMPORTANT:

Never expose the Supabase service-role key in frontend code.

If Storage deletion requires privileged execution, use a secure Supabase Edge Function or SECURITY DEFINER mechanism with proper authorization.

Do not create a new external backend solely for this.

⸻

P1 — RESUMABLE / RECOVERABLE UPLOADS

Audit the current creator upload implementation.

For large music videos:

* upload progress must be accurate;
* temporary network failures should be recoverable;
* retry should not create duplicate database rows;
* incomplete uploads must not become publicly playable videos;
* successful upload should create exactly one video record;
* thumbnail handling must remain reliable;
* creators must receive a clear success/error state.

Prefer Supabase’s supported upload capabilities.

Do NOT build a custom distributed upload service.

If true resumable uploads cannot be safely implemented without expanding V1 architecture, implement the safest supported retry/recovery behavior and document the limitation rather than creating unnecessary infrastructure.

⸻

P1 — MP4 BROWSER COMPATIBILITY

The existing verified media object is:

* valid H.264/AAC
* valid MP4
* correctly served by Supabase Storage
* supports HTTP range requests

A restricted test browser previously reported media error code 4.

Do NOT treat this as a Storage failure.

Do NOT permanently generate WebM derivatives.

Do NOT introduce transcoding merely to satisfy the restricted test browser.

Validate the existing production playback architecture on supported environments:

* Safari/iOS
* Android Chrome
* desktop Chrome
* desktop Safari
* Firefox where appropriate

Confirm:

* direct MP4 playback
* HLS fallback when master_playlist_url exists
* native HLS where supported
* graceful unsupported-browser messaging
* retry behavior
* fullscreen
* seeking
* buffering
* resume playback
* view tracking

If a particular test runtime cannot decode the MP4, document:

BROWSER_LIMITATION

instead of changing Moonirat’s production architecture unnecessarily.
